# Storage

`channels.toml` is the source of truth for channels. SQLite holds what the program derives from it and what happens at run time. The code is in `src/store/` and the schema is in `migrations/`.

The `events` table holds each channel's generated schedule, one row per `timeline::Event`. Rows are keyed by channel number and start time, which is also the index for reading a time range; events of one channel must not overlap. A sequential channel continues after its last stored program event, so there is no separate cursor table; migration 0003 dropped the old `cursors` table. `playback_history` gets one row each time the tuner starts something, with a short outcome word such as `played` or `failed`; a file whose real length differs from its event is recorded as `padded`, `short` or `cut` (`schedule::record_fit`, see [Schedule generator](schedule.md)). A regeneration replaces a channel's events from a boundary with `Store::replace_events_from` in one transaction. `substitutions` (migration 0005) gets one row for each scheduled program a regeneration replaced because its item left the library: the channel, the item, when it was to start, the media now on at that time (or null) and when the row was recorded (`Store::record_substitution`, `Store::substitutions`). All times are Unix epoch milliseconds. `Store` opens the file in WAL mode with a 5 second busy timeout and foreign keys on, and it refuses to write an event that does not end after it starts. For health checks, `Store::schedule_end_ms` gives when a channel's last event ends and `Store::schema_version` the newest applied migration.

The `library_items`, `library_chapters`, `library_streams`, `library_collections` and `library_collection_members` tables (migration 0002) hold a copy of the Jellyfin library: items with runtime, path and sync time, their chapters and video and audio streams, and collections with their members, each in the order Jellyfin returned them. Migration 0004 adds an episode's series id, series name, season and episode number to `library_items`, adds `library_item_labels` for each item's library names, tags and genres, and rebuilds `library_collection_members` with a `member_id` that may be an item id or a series id, so it no longer references `library_items`; `Store::replace_library` checks that each member is a cached item or the series of one. `Store::replace_library` deletes all of it and writes the new copy in one transaction, so a reader sees the old library or the new one and a failed write changes nothing. In that transaction it also compares the old cache with the new items and rewrites the events of an item whose id changed but whose path did not; see [Jellyfin source](jellyfin.md#keeping-the-schedule-in-step). `Store` implements `MediaSource` over these tables, so the rest of surfcult reads the library from the store. See [Jellyfin source](jellyfin.md).

Migrations are numbered SQL files (`migrations/0001_schedule.sql`) compiled into the binary and listed in `src/store/migrate.rs`. On open, each migration the database has not seen runs once, in order, in its own transaction, and is recorded in `schema_migrations`. To change the schema, add the next numbered file and list it; never edit one that has shipped. A database written by a newer build is refused rather than opened. `Store::open_read_only` is the exception: it opens an existing file for reading without migrating it, and is what the read API uses. Migration 0003 (`0003_drop_cursors.sql`) drops the `cursors` table that 0001 created. Migration 0004 (`0004_library_sources.sql`) keeps cached collections; items cached before it have no series, libraries, tags or genres until the next sync. Migration 0005 (`0005_substitutions.sql`) adds `substitutions`.
